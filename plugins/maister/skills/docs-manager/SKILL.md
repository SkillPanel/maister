# Documentation Manager (Internal Engine)

Internal skill that manages documentation file operations in `.maister/docs/`. Not directly user-invocable — called by `maister:init`, `standards-update`, and `standards-discover` skills, and by a workflow's finalization to consolidate its standard candidates.

## Core Principles

- **Project documentation is source of truth** — plugin-bundled docs are baseline/reference only
- **INDEX.md is a written map that only this skill writes** — one short entry per document, changed only through Refresh INDEX.md
- **CLAUDE.md integration is mandatory** — ensures AI reads documentation
- **The caller asks; this skill never does** — it runs inside the `docs-operator` subagent, which has no user channel

## Decisions Go to the Caller

Every operation below takes its choices from the caller's prompt. When an operation reaches a choice the prompt does not settle, it does not ask: it stops short of that change, finishes what it can, and returns the choice under `decisions_needed` — the question in the user's words, its options with what each changes, and the recommended one with its reason. The calling skill (init, standards-update, standards-discover) asks it and calls again with the answer. Choices a caller has already asked — init's re-initialization question, standards-update's file and merge choices, the built-in edits a person chose — are never returned a second time.

## Documentation Structure

```
.maister/docs/
├── INDEX.md                      # Master index - READ THIS FIRST
├── project/                      # Project-level documentation (generated by maister:init, not copied from templates)
│   ├── vision.md                # Project vision and goals
│   ├── roadmap.md               # Development roadmap
│   ├── tech-stack.md            # Technology choices and rationale
│   └── architecture.md          # System architecture (optional)
├── <any folder>/                # Any other Markdown, copied in as it is (indexed as project docs)
└── standards/                    # Technical standards and conventions, one folder per group
    ├── global/                  # In every project
    ├── testing/                 # In every project
    └── <group>/                 # The groups that fit the code, or the project's own (the table: docs/standards-groups.json)
```

`design-context/` at the top of `.maister/docs/` is the mockup studio's grounding pack, outside the index: its files need no INDEX entry and the docs check skips them.

## Standard File Conventions

Standard files follow the structure `standards/[category]/[topic].md`:
- **Category** = a group: a folder under `standards/`, one of the groups in `docs/standards-groups.json` or the project's own
- **Topic file** = contains multiple related standards

**Format**: Each file uses `## Topic` as the file heading, with `### Standard Name` for each individual standard. Each standard has a 1-10 line description (excluding code snippets) and an optional brief code example (under 10 lines).

**Conciseness**: Standards are quick-reference conventions, not tutorials. A rule holds no inventory of call sites, no dates and no ticket references — the code and its history answer those.

**Size guidance**: about 12 KB or 15 `###` rules per file. Past it, split the file into topic files in the same folder, or move a topic that has grown several files into a sub-folder (`standards/backend/storage/locking.md`): a folder is a group and needs no metadata. The check warns on a file past the guide; nothing refuses one.

**Why ### per standard**: Each standard as a discrete section makes it easier for agents to find, update, and reference individually — no need to parse bullet lists.

## Bundled Resources

This skill bundles the following resources within the plugin:

- **Standards directory**: `docs/standards/`, the baseline standards, one folder per group
- **Group table**: `docs/standards-groups.json`, one entry per group with its folder, files, the profile conditions that select it and its discovery file filter. `scripts/standards.mjs groups` applies it; prose never restates it
- **Rename and removal map**: `docs/standards-map.json`, beside the group table: each built-in rule an earlier version shipped, with the text it shipped, what became of it and where its rule lives now, and the rules added since. `scripts/standards.mjs built-in candidates` applies it; prose never restates it
- **INDEX.md Template**: Master template for documentation index
- **Standard candidates**: `references/standard-candidates.md` — the one description of a standard candidate: what it is, how one is written, where it belongs, and how finalization consolidates them
- **Index check**: `scripts/docs-check.mjs` — reports whether INDEX.md still maps the documents (see Refresh INDEX.md)
- **Group resolver**: `scripts/standards.mjs`, beside the index check, answers which groups fit a project (`groups`) and which built-in rules changed since a project's copy was made (`built-in candidates`)

## Location Reference

- **Plugin bundles** (read-only baseline): This skill's `docs/` subdirectory within the plugin
- **Project documentation** (source of truth): `.maister/docs/` in the project root
- **Project configuration**: `CLAUDE.md` in the project root

## Capabilities

### 1. Initialize Documentation in Project

Use this when a project doesn't have `.maister/docs/` or needs documentation for the first time. This is a **one-time baseline setup** that gives the project a starting point.

**IMPORTANT**: This operation requires a `standards_selection` parameter (array of folder names) that says which standards to initialize. It also accepts an optional `standards_source_path` parameter to copy standards from an external project instead of the bundled defaults.

**What to do:**
1. Check if `.maister/docs/` exists in the project root
2. If it exists, proceed only when the caller's prompt says so (init asks before re-initializing); otherwise return the overwrite as a decision needed
3. Create the directory structure:
   ```
   .maister/docs/
   ├── project/
   └── standards/<folder>/    for each selected folder
   ```
4. Copy each selected folder by name — a group of the group table (`docs/standards-groups.json`) or the project's own — whole (its files and sub-folders), from `standards_source_path`, or else from this skill's bundled `docs/standards/`. A selected name the source does not hold is created empty, as the project's own group. Example: `['global', 'testing', 'cli', 'data']` copies those four folders.
   - **Project documentation**: Do NOT copy project templates — only create the `project/` directory. Project documentation files (vision, roadmap, tech-stack, architecture) are generated by the calling skill (e.g., maister:init) using analyzer data, not copied as placeholder templates.
5. Write INDEX.md with Refresh INDEX.md — every copied file is new — one `## Standards: <folder>` section per copied folder; a folder that was not copied gets no section: the index maps only what the project holds.
6. **MANDATORY - Update CLAUDE.md:**
   - Check if `CLAUDE.md` exists in the project root; if not, create it — the integration is mandatory — and name it in the result
   - Add the documentation reference section (see "Manage CLAUDE.md Integration" operation)
   - Ensure it emphasizes reading INDEX.md at the beginning of any task
7. Inform the caller about the documentation structure created

**Parameters:**
- `standards_selection` (required, array of strings): Folder names to initialize
  - Folder names under `standards/` (e.g., `['global', 'testing', 'data']`): a group of the group table or the project's own
  - If omitted or empty: no standards are copied, and the selection is returned as a decision needed
- `standards_source_path` (optional, string): Absolute path to an external standards directory (e.g., `/path/to/other-project/.maister/docs/standards/`); the bundled `docs/standards/` tree's own absolute path is a valid value too, and copies the defaults
  - If provided: Copy standards from this path instead of the bundled defaults
  - If omitted: Copy from this skill's bundled `docs/standards/` directory (default behavior)

**Result:** The project now has baseline documentation in `.maister/docs/`, an INDEX.md that maps it, and CLAUDE.md integration that ensures AI assistance is documentation-aware. Only the selected folders are initialized.

**Important:** After this initial setup, the project's documentation becomes the source of truth. Teams should customize it for their specific needs.

**Note on Skipped Standards**: If groups are skipped during initialization, teams can add them later using:
- "Add Documentation File" operation to add specific standards
- `/maister:standards-discover --scope=<group>` command to auto-discover a group's standards from the codebase

### 2. Refresh INDEX.md

The one operation that writes `.maister/docs/INDEX.md`. Every other operation here, and every caller, changes the index only through it. It takes:
- `changed` (optional): paths under `.maister/docs/` the caller added, changed or removed
- `check` (optional): the absolute path of `docs-check.mjs`; without one, find it under this plugin's docs-manager skill, in `scripts/`
- `reshape` (optional): only when the operator asks to bring an existing index back in shape

**What to do:**
1. **Run the check** from the project root (`node <check path>`). Its failures name the work: `unindexed-file` is a new document, `dead-entry` a gone one, `duplicate-entry` and `conflict-marker` a damaged index, `index-missing` an index to write.
2. **Collect the targets**: those documents, plus `changed`. With no `changed` given, take what changed under `.maister/docs/` since INDEX.md was last committed — the commit `git log -1` names for INDEX.md, `git diff --name-only` from it, and `git status` — or, without git, the check's findings alone. With `reshape`, also every entry the check warns on.
3. **Settle a conflicted index** by keeping both sides' entries and dropping the markers; a path left with two entries becomes a target. Never merge entry prose by hand.
4. **Write each target's entry** (rules below). Read the document's first heading and opening paragraph, and the whole file only when those do not say what it is for. A changed document whose purpose did not change keeps its entry; a gone document loses it.
5. **Keep everything else byte for byte** — every other entry and the text around them — so two branches that refresh different documents merge cleanly. Three things are applied every time: the header comment from `references/index-md-template.md` is added when missing; the retired "Keep Updated" and "Updating Documentation" guidance, which tells readers to edit the index, is removed; and the placeholder an earlier Initialize wrote for a skipped category — a "Not initialized" line under a `## Standards: <folder>` heading and the bullets right under it — is removed, with its heading when no entry sits under it. With `reshape`, the layout is also brought to the template: sections by kind and folder, entries at `###`.
6. **Run the check again** and return its result: the files and entries it counted, any failure left (an error in this refresh, to be fixed before returning) and its warnings.

A helper script for any of these steps, when one is written, goes in the `scratch:` folder the caller names, else in the directory `node <plugin root>/skills/workflow-engine/scripts/workflow.mjs scratch-dir --for=docs-index` makes and prints, the plugin root two levels above this skill's base directory: under `.maister/scratch/`, which git ignores, never the session's scratchpad or the system temp directory.

**Where an entry goes.** The kind follows from the path alone. A document under `standards/` is a standard; anything else is a project doc, files copied in from elsewhere included. Project docs go under "Project documentation" — `project/` and the top-level files — or under one "Project documentation: <folder>" section per other folder; the workflows' intake reads project documents from these sections. Standards go under one `## Standards: <folder>` section per folder, so `standards/backend/storage/` has its own. Entries run in path order within a section.

**The entry.** ``### <title> (`<path>`)``, the path relative to `.maister/docs/`, then one or two sentences:
- **Title**: the document's first heading, else its file name without the extension.
- **A project doc** says what question it answers and when to open it — "How releases are cut and promoted. Open when a change touches versioning or CI." About 240 characters.
- **A standard** says what code or task it governs, then `Read in full before:` and up to about eight topics: noun phrases naming situations, taken from its `###` rule headings, never the rules themselves — "How data is read and written safely and fast. Read in full before: SQL and ORM queries, N+1 risks, transactions, timeouts, caching." About 300 characters.
- **Never in an entry**: counts of things, dates, ticket or PR references, history ("amended", "note"), or restated rules and facts. An entry says where to look; the document says what is there. The check warns on each, and on an entry past its size guide.

**Result:** INDEX.md maps every document, the entries this refresh did not target unchanged, and the check passes.

### 3. Add Documentation File

Use this to add new documentation to the project, either from plugin baseline or custom.

**What to do:**
1. Determine the type of documentation to add:
   - Project documentation (vision, roadmap, tech-stack, architecture, custom)
   - Technical standard (any category under standards/)
2. If adding from plugin baseline:
   - Check if the requested documentation exists in this skill's bundled `docs/` directory
   - Copy it to the appropriate location in `.maister/docs/`
3. If creating custom documentation:
   - Take the category (project/ or standards/category/), filename and purpose from the caller; any missing goes back as a decision needed
   - Create the file with a first heading and an opening paragraph saying what it is for; no frontmatter is needed
4. Refresh INDEX.md with the new path as `changed`
5. If this is a technical standard and corresponds to a project skill, ensure consistency

**Result:** New documentation is added to the project and has its entry in INDEX.md.

### 4. Update Documentation

Use this to help the user update or modify existing project documentation.

**What to do:**
1. Accept the documentation identifier from the user (e.g., "project/vision", "standards/global/error-handling")
2. Check if the documentation exists in `.maister/docs/` — or, for the project's contributor guide, at the path the caller names outside it
3. If the documentation exists:
   - Read the current documentation
   - Apply the change the caller describes, and only that; with none described, return the question as a decision needed. A section the caller does not name for replacement or removal stays as it is: content that overlaps it is added beside it or to it, never folded into a new section in its place
   - Include the plugin's baseline version for reference when the caller asks for it
4. If the documentation doesn't exist, return a decision needed: add it from the plugin baseline ("Add Documentation File") or create it from scratch, except a built-in edit's home file, which is created
5. After updating:
   - Refresh INDEX.md with the path as `changed`; its entry changes only when the file's purpose did. A contributor guide outside `.maister/docs/` has no entry and gets no refresh
   - If updating tech-stack.md or architecture.md, suggest reviewing CLAUDE.md for consistency
6. For technical standards:
   - If a corresponding project skill exists, suggest reviewing it for consistency
   - Standards should align with actual code patterns in the project

**Built-in standard edits.** A call that names built-in edits applies each one as add, replace, remove or move; a merge is removals plus one write. Every section the call does not name stays byte for byte. A section runs from its `###` line to the next `#`, `##` or `###` heading outside a code fence, or to the end of the file.
- **Placement.** When, after the edit's removals, the file already holds a `###` section with the home heading at the time of the edit (an earlier edit in this call wrote it), nothing is written; the removals still apply. Otherwise the new section goes in place of the first section the edit removes from that file. When the edit removes none there, it goes directly after the file's `#`/`##` title lines when the given preceding list is empty; else after the first heading of that list that the file holds at the time of the edit; when the file holds none of the listed headings, at the end. Sections are separated by one blank line, and the file ends with one newline.
- **Files.** A missing home file is created with the given `## ` title line, a blank line, then the section. A file left with no `###` section and nothing but `#`/`##` headings and blank lines is deleted. A file that keeps other text stays, and the result names it.
- **Guarded removal.** A section is removed only while its text still equals the text the call gives, compared with each whitespace run made one space, trailing spaces trimmed on each line, line endings made LF and leading and trailing blank lines dropped. Otherwise the whole edit is not applied: no section of it is removed and nothing is written, and its reason names the changed section. No choice is returned as a decision needed: the caller has asked them all already.

**Result:** Documentation is updated to reflect current project state and team decisions.

### 5. List Available Documentation

Use this to show what documentation is bundled with this plugin and their installation status in the project.

**What to do:**
1. List all documentation in this skill's bundled `docs/` directory, organized by category; only the Markdown documents under `docs/` count, and `docs/standards-groups.json` and `docs/standards-map.json` are data, never listed or copied
2. For each bundled document:
   - Show the category and name
   - Check if it exists in the project at `.maister/docs/[category]/[name].md`
   - Show installation status (bundled only, installed, or customized)
   - If installed, show whether it differs from the baseline (customized)
3. Show whether INDEX.md maps every document — the check's result
4. Show whether CLAUDE.md has documentation integration
5. Remind the user that plugin documentation is baseline/reference only, and project documentation (if installed) is the source of truth

**Result:** The user sees a complete inventory of available baseline documentation and their installation status in the current project.

### 6. Manage CLAUDE.md Integration

Use this to ensure the project's CLAUDE.md properly integrates with the documentation system, encouraging AI to read and use the documentation.

**What to do:**
1. Check if `CLAUDE.md` exists in the project root
2. If it doesn't exist, create it — the integration is mandatory — and name it in the result
3. Look for a documentation reference section in CLAUDE.md
4. If the section doesn't exist or is incomplete:
   - Read `references/claude-md-template.md` for the template
   - Add the template section to CLAUDE.md
5. Ensure the documentation section is placed prominently in CLAUDE.md (near the top)
6. Verify that the INDEX.md path is correct and the file exists, reading the path from the folder the instructions file sits in
7. If `.maister/docs/` doesn't exist, suggest running the initialization operation first

**Result:** CLAUDE.md properly integrates with the documentation system, ensuring AI assistance is documentation-aware and follows team conventions.

### 7. Validate Documentation Consistency

Use this to check that documentation is consistent, up-to-date, and properly integrated.

**What to do:**
1. **Check structure:**
   - Verify `.maister/docs/` directory exists
   - Verify all expected subdirectories exist (project/, standards/global/, etc.)
2. **Check INDEX.md:** run the check and report its failures (unindexed documents, dead or duplicate entries, conflict markers) and its warnings (entries past their guide, dates, ticket references, counts, standards files past their guide)
3. **Check CLAUDE.md integration:**
   - Verify CLAUDE.md exists
   - Verify it contains documentation reference section
   - Verify it uses valid file reference format: @.maister/docs/INDEX.md (with @ prefix, without backticks)
   - Warn if using incorrect formats like `.maister/docs/INDEX.md` or `@.maister/docs/INDEX.md` (backticks)
4. **Check project documentation:**
   - Verify critical files exist (vision.md, tech-stack.md)
   - Check if they contain placeholder text vs. actual project information
   - Warn if critical documentation is missing or empty
5. **Check standards consistency:**
   - If project skills exist, check if corresponding standards documentation exists
   - If standards exist without skills, suggest creating skills (if appropriate)
   - Report any inconsistencies
6. **Generate validation report:**
   - Summary of documentation status
   - List of issues found
   - Recommendations for fixes
7. **Fix what is safe to fix:**
   - Fix the check's failures with Refresh INDEX.md, and missing CLAUDE.md integration and missing directory structure, without asking — they only add what the documentation system requires
   - Return anything that would change the team's own content as a decision needed

**Result:** A comprehensive validation report with optional automatic fixes for common issues.

### 8. Consolidate Standard Candidates

Use this at a workflow's finalization, before the run writes its candidates file. Read-only: it writes no document and refreshes no index.

**What to do:** follow *Consolidation* in `references/standard-candidates.md` over the candidate lines the caller passes and against the open queue of earlier runs it passes beside them, with the project's own wording from its `CLAUDE.md` block and the top of INDEX.md taking precedence over that file's description. Return the consolidated list — at most five new lessons — the attachments, the already-held lines and how many lessons were dropped over that cap, as that section says; no choice is returned as a decision needed — the caller writes the list to the run's candidates file, and the person chooses later, through standards-update.

**Result:** fewer, clearer candidates, each with its suggested destination and its evidence, for the person to choose from when they run standards-update; a lesson an earlier run already filed counts as support for that candidate instead of being filed again.

## Guidance for Projects

What a team keeping its documentation in `.maister/docs/` should know:
- **INDEX.md is maintained by maister.** Nobody edits it by hand: change the source document, and the next refresh updates its entry — at the points a workflow runs one, or with `/maister:standards-update --refresh-index`.
- **A merge conflict in INDEX.md is fixed by a refresh**, never by hand-merging the entries.
- **Tests and handoffs pin facts in the source documents**, never in INDEX.md. An entry says where to look, not what is there, so a fact pinned to it pins the wrong file.
- **Any Markdown file may live in `.maister/docs/`**, copied in as it is. No frontmatter, schema or naming is required.
