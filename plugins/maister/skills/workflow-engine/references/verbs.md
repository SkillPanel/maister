# Verbs

The workflow engine's verbs: the twelve every run calls (§ *The verbs every run calls*), the ones
that only some steps and the runner subagents call (§ *The verbs some steps call*), the model
and effort every agent call carries (§ *Model and effort on every agent call*), and the
refusals of every verb. The invocation — one command starting with the engine path, the
here-string or the patch file, the exit codes — is the engine skill's § *The invocation
contract*. An italic section name below is the engine skill's, unless a file is named. Each
refusal is also printed by the verb that refuses. A usage error (exit `2`) prints its own `usage:`
line, then the verb's whole usage line — every flag it takes, the optional ones in brackets — so
one retry can fix every flag.

## The verbs every run calls

| Verb | Flags | Gives |
|---|---|---|
| `validate` | `--definition`, repeatable `--overlay`, `--profile` | `{ok, errors[], warnings[], resolved[]}` on stdout — `resolved` says where each target was found. Every profile the overlays declare is judged, selected or not, and a finding only one profile produces is prefixed with its name. What each warning means is `references/grammar.md` § 14 |
| `resolve` | `--definition`, `--overlay…`, `--profile` (a profile one of the overlays declares; selecting any other is refused) | the canonical graph, its `graph_hash` **in the spelling state records** — write it through unchanged, never re-spell it — and `tracker_key`, the input the freeze reads for `task.key`, or null |
| `locate` | optional `--name` (bare or `builtin:`-prefixed); with it, repeatable `--overlay` and `--profile` — the run's own | with a name, where the lookup (engine *Resolve the workflow by name*) finds it: `{ok, errors[], name, from, definition, overlays[], ignored, companion, title, summary, inputs, dispatches[], html_companions}` — `definition` and `overlays` are the values the three verbs above take, a project path written relative to the project root; `dispatches` names the nodes carrying `dir:` in the folded graph, and `html_companions` is the block merged from every layer (`{}` when none declares one). Exit `1` when the name is found nowhere, is not a workflow name, finds only an overlay with no built-in beneath it, or finds a file whose `name:` is another. With no name, `{ok, errors[], workflows[]}` — the project's own definitions. Reads only. On a Node.js older than 20 it prints only `RUN-FAILED: node-unavailable` on stdout and the 2.x install line on stderr, exit `1`, a marker and not a refusal (engine *Step 2*) |
| `write-state` | `--state`; the patch as JSON by here-string, or `--patch-file` naming it in the patch file; optional `--host` (`claude` or `copilot`; the freeze records the delegation of the host it names, else of the host this build ships for); optional `--no-open` | the changed paths, one per line; the freeze prints the startup banner and a blank line before them (engine *Freeze the graph before executing anything*), and opens the dashboard in the browser for a run driven from the terminal unless `--no-open` or `MAISTER_NO_OPEN` is set. A write carrying a node's question set adds a blank line and `ask: <id> <id> …`, or `ask: none` (`references/in-node-questions.md` § *When the policy classes a question*). A write completing a node whose owed `.html` companion is not on disk ends with a blank line and one `companion-missing: <node> <path>` line per companion, then, in the same paragraph, one `companion-stale: <node> <path>` line per companion of any completed node that is older than its markdown, and last in that paragraph `rules:` naming `references/writing-state.md` § *A missing or stale companion*, exit `0`. A write that completes or skips a node ends with a blank line and `next: <id> (<title>) — run node-brief for it`, the first pending node in frozen order whose needs are settled, or `next: none — write the closing patch with task.status, then run run-complete` when nothing else is left; it prints none while a step is waiting or running with nothing else due, nor on the closing patch itself (engine *The ready set*). The closing checkpoint `held-approval` is written under `node_summaries.held-approval`, and its `status` under `nodes` (`references/gates.md` § *The closing checkpoint `held-approval`*) |
| `gate-request` | `--state`, `--node`, and `--reask` or `--patch-file` (the node's question set); or `--state` and the request as JSON by here-string or in the patch file | the files written, one per line: the request file, the gate index and the pending marker, in one call (`references/gates.md` § *Driver-suspended mode — the write order*) |
| `gate-revise` | `--state`, `--node` (the gate), `--option` (its revise option); `{note, answered_by?, at?, via?}` by here-string, or `--patch-file` naming it in the patch file | the changed paths, one per line, then a blank line and `revised: <gate> reruns=<node> revision=<n>/10 reset=<ids>`: the stretch from the option's rerun node to the gate reset in one write, with the note on the gate (`references/gates.md` § *Revising at a gate*) |
| `run-complete` | `--state`, and in a dispatched run `--outbox` and `--dispatch-id` | the run's closing marker as the **last** line of stdout, with any `missing-artifact:` lines, then any `missing-companion:` lines, and a stop's notice above it; the refusal on stderr |
| `prior-context` | `--state`, optional `--background`, optional `--node` | the prior phases' decisions and risks as markdown, to paste into a delegate prompt, each decision one numbered line — what was decided, who settled it, its question id — whose full item is `node_summaries.<node>.decisions[n]` in the state file the passage names once; `--background` frames them as background for a document written for end users; `--node` prints that node's `run-context` block first, then one blank line, then the same passage, with `run-context`'s refusals; a context block whose retired `phase_summaries` mirror still holds a decision or a risk adds one `warning: legacy-mirror-ignored:` line counting its decisions and risks, which `resume-check` already relayed at resume, so it is not repeated to the user, exit `0` — reads the run, writes nothing |
| `run-context` | `--state`, `--node` (the node about to delegate) | the run-scoped context a delegate prompt carries, as markdown to paste unedited (engine *Before anything else*, **Every delegate prompt carries the run's context, fetched**), with a `grounding pack` line when the project has `.maister/docs/design-context/` and the run's workflow declares `changes_code: true`, saying the change never edits or rebuilds it, and the `summary contract:` line only for a node that declares a markdown artifact (both print when the definition cannot be re-read); when the definition the run froze cannot be re-read, `companions: unknown` and one `warning: run-context-definition-unread` line, exit `0` — reads the run, writes nothing |
| `node-brief` | `--state`, `--node` (the node about to run) | What the node reads before it runs, as markdown: how it runs — for an `agent:` step with the model and effort its call carries, as `dispatch-model` resolves them, and for a `direct:` step whose `brief:` declares `delegates` for the run's host a `delegates:` line with each agent of that set beside its model and effort — its guard and attempt, its `with:` values and `dir:` filled in, the files it writes with the pages it owes and the absences `brief:` allows, its questions under this run's driver, the checkpoint it feeds, its `brief:` data, the convention rows that apply now, each printed whole the first time this session's briefs meet it and named on one `conventions in force (…)` line after that, until a resume or a compaction — a row that applies only later, under a recorded revise or on a last attempt, named on one `convention (…): see rules` line — for an `agent:`, `skill:` or `direct:` step run here, a `closing patch` line giving the closing write's exact keys with each value a placeholder, and a `rules:` line, then the node's own section. A ready step still `pending` is recorded `running` by it, with a `started:` line; a write it could not make is one `warning: node-brief-start-unrecorded` line. A line that would only state the default (no guard, a first attempt not yet run, an unset recommends input) is left out. A gate gets the `gate-brief` call instead, unless its section carries an exception. Graph drift, an unread definition, a node the definition no longer carries or an unread conventions table is one `warning: node-brief-…` line, exit `0` — reads the run, and writes only the start and, with a session id, the session's conventions marker under the project's `.maister/display/` |
| `gate-brief` | `--state`, `--node` (the gate), and at most one of: `--json` with `--picker=rich`, `--ask` (optionally with `--note=<revise option>` or `--details`), `--checkpoint`, `--request` or `--oneline`; or `--node` (a running node) with `--checkpoint`, `--request` or `--ask` and `--patch-file` — the node's question set as JSON in the patch file | The brief for a gate, or for a running node's question set. It writes no state, only the run's `display/next.json`. `--ask` prints nothing but the arguments of a labels-only question tool's call, to pass as they stand. With no form, the brief as text within 1,600 characters, plus the trailing `rules:` line; `--node=held-approval` briefs the run's closing checkpoint. Each form's shape is `references/gates.md` § *The `gate-brief` forms* |
| `resume-check` | optional `--state`, optional `--no-open` | JSON on stdout: the frozen workflow's `name`, `overlays` and `profile`, the run's `driver_kind`, its `root` (its checkout, derived from where the state file is) and its `dashboard` link (`null` when it has none), while a gate is pending its `gate` with what is on disk for it (*Resume*), or, exit `1`, the refusal of a directory the engine does not resume, with an operator `message` (*Resume*); for a run it accepts it also opens the dashboard in the browser, as the freeze does, unless `--no-open`; a retired `phase_summaries` mirror in the context block that holds a decision or a risk is one `warning: legacy-mirror-ignored:` line on stderr, outside the JSON, exit `0` — reads the run and writes nothing in it; for a run it accepts it records the session's display pointer, under the project's `.maister/display/`, and removes the session's conventions marker there, so the next `node-brief` prints the node conventions whole; one that cannot be written or removed is a `warning:` line on stderr; with no `--state`, run from the project root, it lists the runs waiting on a gate under `waiting` and exits `0` however many there are, opening nothing and writing nothing, the pointer included. On a Node.js older than 20, either form prints only `RUN-FAILED: node-unavailable` on stdout and the 2.x install line on stderr, exit `1` (engine *Step 2*) |

## Model and effort on every agent call

A project chooses the model and effort its subagents run on (`subagents` in `.maister/config.yml`, `references/writing-state.md` § *Project configuration*), and the engine resolves the choice; the call only carries it. An `agent:` node's call takes the values its brief's `runs:` line prints. Every other agent call — a skill's or a command's fan-out, a `direct:` step's delegate, a fix, an HTML companion or an index refresh — takes them from the engine's `dispatch-model` verb:

- **Run it once, just before the fan-out**, naming every agent type the fan-out uses: `node ${CLAUDE_PLUGIN_ROOT}/skills/workflow-engine/scripts/workflow.mjs dispatch-model --agent=<type>[,<type>…] --host=claude`. Inside a run add `--state=<task path>/orchestrator-state.yml --node=<the node under way>` (its `orchestrator.started_phase`); standalone, add neither. Run it again before each later fan-out rather than reusing an earlier line, so the value is in context at the call and survives a compaction.
- **Copy, never work out.** Each line reads `<agent>: model <m>, effort <e> — source: …`; copy its two values into the call's `model` and `effort` fields, beside `subagent_type`, and leave out a field printed as `omit`, so the host's own choice applies. A `note:` line is acted on where the caller says so (the implementation executor's budget); otherwise it needs nothing.
- **When the host refuses a field** — a model it lacks, an effort an older host does not take — send the call again without that field and write one warning line saying which field and agent: in the work log when the caller keeps one, else in the node summary's `risks` as a `tradeoff`, else in the reply. A verb that cannot run at all is the same: dispatch without either field and say so once. A missing value costs money, never the call.
