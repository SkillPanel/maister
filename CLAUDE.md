# CLAUDE.md

Claude Code plugin marketplace for **Maister** — structured, standards-aware SDLC workflows. Plugin source is `plugins/maister/`; `plugins/maister-copilot/` is a generated GitHub Copilot CLI variant.

This file guides work **on this repository**. Plugin consumers never see it — runtime behavior (phases, gates, delegation, artifact contracts) must live in `SKILL.md`, agent, and reference files under `plugins/maister/`, never here.

## Layout

```
.claude-plugin/marketplace.json   # Marketplace manifest: name, version, plugin list
.claude/rules/                    # Path-scoped authoring rules (auto-load when editing plugin source)
plugins/maister/                  # Plugin source — edit here
  .claude-plugin/plugin.json      #   Plugin manifest
  lib/*.mjs                       #   Executable code shared by more than one skill
  skills/<name>/SKILL.md          #   Skills (+ optional references/, assets/, server/)
  agents/*.md                     #   Subagents
  commands/*.md                   #   Slash commands (thin wrappers; flat, no subdirs)
  skills/*/schemas/*.json         #   Contract JSON Schemas (orchestrator-framework)
  hooks/hooks.json                #   Lifecycle hooks; `*.sh` guards + `*.mjs` gate hooks alongside
  .mcp.json                       #   Playwright MCP server
plugins/maister-copilot/          # GENERATED by `make build` — never edit by hand
platforms/claude-code/            # `--settings` hook template for chain-mode sessions
platforms/copilot-cli/build.sh    # The generator
platforms/copilot-cli/hooks/      # Copilot hook registration + install notes (→ .github/hooks/)
fixtures/contracts/               # Golden fixtures for `make test` — nothing reads them at runtime
scripts/                          # Node tooling: contract suite, eval harness, tarball builder
eval/                             # Local gate-hook evaluation harness (`results/` git-ignored)
docs/                             # User-facing docs (workflows.md, commands.md)
docs/decisions/                   # Plugin decision log (ADRs) + index
README.md                         # User-facing install/usage
```

## Hard rules

- **Never edit `plugins/maister-copilot/`.** It is generated from `plugins/maister/` by `make build` and is *committed* (the marketplace manifest points at it). CI rebuilds and commits it on pushes to `master`; on other branches run `make build && make validate` yourself and commit the regenerated output alongside the source change.
- **`SKILL.md` is uppercase.** Skills live at `skills/<name>/SKILL.md`.
- **Contract-bearing shapes change only through `compatibility-contracts.md` + schemas + fixtures in one change.** A schema edit without a register row and a fixture is drift, not a decision; `make test` is what proves the three agree.
- **The compatibility floor is plugin 2.2.3.** The frozen shapes describe task directories written by 2.2.3 or newer; older ones are listed by name/date/type only — never parsed, rendered or resumed. No migration path exists, and none is to be added (`docs/decisions/0006-compatibility-floor.md`).
- **Inventories are not kept here.** Skills, agents, and commands are self-describing via frontmatter — `ls` the directories instead of expecting a catalog in this file.

## Commands

| Command | Purpose |
|---|---|
| `make build` | Regenerate `plugins/maister-copilot/` from `plugins/maister/` |
| `make validate` | Lint the generated variant (flat commands, no colons, no multi-select, no `maister:` prefixes) plus the gate-marker lint over the plugin source |
| `make test` | Run the compatibility contracts suite (`scripts/verify-contracts.mjs`: schemas, fixtures, hook replay) |
| `make eval` | Run the gate-hook evaluation locally on both providers (needs authenticated CLIs; never in CI) |
| `make tarball` | Build the `contracts-v1` archive (schemas, fixtures, manifest, runner, checksum) |
| `make clean` | Delete the generated variant |
| `make watch` | Rebuild on change (requires `fswatch`) |

`make test` runs the compatibility contracts suite (schemas, fixtures, hook replay); `make eval` runs the local gate-hook evaluation on both providers (needs authenticated CLIs). Behavioural testing on top of them: in a scratch project run `/maister:init`, then a workflow such as `/maister:development "test feature"`, and inspect the task directory under `.maister/tasks/`.

## Non-obvious behaviors

- **Skills and agents are not interchangeable.** Skills run in the main agent via the Skill tool (they may spawn subagents; subagents cannot spawn subagents). Agents run via the Task tool. Details: `orchestrator-patterns.md` § 1.
- **Destructive-command guard.** `hooks/block-destructive-commands.sh` blocks `git stash`, `reset --hard`, `checkout .`, `clean`, `push --force`, `rm -rf` for every subagent except those in its `case` whitelist. `task-group-implementer` is deliberately *not* whitelisted (it runs in parallel waves). Add an agent only if it genuinely needs full Bash.
- **Session-start hooks inject rules into every consumer session** (`hooks/skill-invocation-reminder.sh`, `hooks/post-compact-reminder.sh`): `/maister:*` commands must be invoked via the Skill tool first, and orchestrators must `AskUserQuestion` at every gate. Don't write skill/agent prose that contradicts them.
- **The gate rule is qualified by the driver.** An orchestrator must ask in-session when `orchestrator.driver.kind` is absent or `terminal`, and must NOT ask when it is `cockpit` or `dispatch` — there it suspends the run with one `gate-request` call — the engine verb that writes the request file, the gate index and `gate_pending` together — prints `GATE-PENDING: <node>` and ends the turn (`compatibility-contracts.md § E2`). Both reminder hooks, the stop nudge, the six orchestrator Step-0 blocks — the workflow engine's own included — the framework patterns, the register's E2 rules, the worker seed and this file all carry the same rule; change them in lockstep. `make test`'s `gate-sequence-lockstep` check enforces it: every carrier must name the `gate-request` verb, claim it as one call, and carry no two-write sequence.
- **Gate hooks.** `hooks/gate-enforce.mjs` runs on every mutating tool call; it allows instantly when no `gate_pending` exists under `cwd`. `hooks/gate-stop-nudge.mjs` runs on every `Stop` and blocks only a run whose `driver.kind` is `cockpit` or `dispatch` — under an absent, `terminal` or unreadable kind no request file is owed, so it stays silent and a terminal operator never sees it. Both are registered in `hooks.json`, and the nudge is registered **only** there: nothing deduplicates a hook, so a second registration would fire it twice. Chain-mode sessions also load `platforms/claude-code/gate-hooks.settings.json`, which adds the liveness beacon and a matcher-free copy of the gate hook. The beacon is written to `$MAISTER_BEACON_DIR` (default `~/.maister-cockpit/beacons/`), never into the project.
- **Never auto-rollback.** On failure workflows stop, analyze, and ask the user (`implementation-plan-executor/SKILL.md`).
- **Artifacts are anchored to the task directory.** Everything a workflow produces goes under `.maister/tasks/<type>/<YYYY-MM-DD-name>/`, never into project directories.
- **The Copilot build rewrites source.** `build.sh` strips `maister:` prefixes, flattens commands, rewrites `multi-select` → sequential single-select, `AskUserQuestion` → `ask_user`, and `CLAUDE.md` → `.github/copilot-instructions.md` in skills. Write source that stays correct after those substitutions.

## Branches & releases

- `master` — stable. Marketplace name `maister-plugins`, version `X.Y.Z`.
- `beta` — pre-release. Marketplace name `maister-plugins-beta`, version `X.Y.Z-beta.N`.
- The version lives in three manifests: `.claude-plugin/marketplace.json`, `plugins/maister/.claude-plugin/plugin.json`, `plugins/maister-copilot/.claude-plugin/plugin.json`. Bump in its own commit (`Bump version to X.Y.Z`).
- Pushing a `vX.Y.Z` tag triggers CI: build, validate, GitHub release with generated notes.
- `.gitattributes` forces LF on `*.sh`, `*.mjs`, `*.json`, `*.yml` and `*.js` — the hooks are invoked by explicit interpreter and must not acquire CRLF on a Windows checkout.

**Promoting beta → master (squash workflow):**

1. `git checkout beta && git merge master`
2. `git checkout master && git merge --squash beta`
3. Set name `maister-plugins` and the release version in all three manifests; commit the feature; bump version in a separate commit
4. `git checkout beta && git reset --hard master` — squash leaves no merge parent, so a later `merge master` into beta would replay old commits and conflict
5. Set name `maister-plugins-beta` and version `X.Y.Z-beta.1`; commit; `git push origin master beta`
